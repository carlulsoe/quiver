# crAPI read-only benchmark ground truth

## Scope

This note defines the eval-only ground truth in `crapi-benchmark.ts`. It is intentionally absent from the runtime campaign engine and target profile so that the system under test cannot use the answer key.

The local target is OWASP crAPI version `1.1.5` at commit `73d309cc8f28bbdeed31dbb35f05dba8354de3c9`. The benchmark includes only vulnerabilities that the current campaign can demonstrate with observation-oriented HTTP `GET` requests and its normal or absent authentication. OWASP describes crAPI as intentionally vulnerable and asks testers to discover as many vulnerabilities as possible ([official challenge introduction](https://github.com/OWASP/crAPI/blob/73d309cc8f28bbdeed31dbb35f05dba8354de3c9/docs/challenges.md#intro)).

Endpoint matching normalizes numeric and UUID path segments to `{id}` and ignores query strings. Data-exposure findings accept either the runtime's `excessive-data-exposure` or `sensitive-data-exposure` label. Unauthenticated order access accepts the runtime taxonomy labels that can reasonably express the issue because that taxonomy currently has no dedicated unauthenticated-access category.

## Safe controls

Safe controls are category-specific rather than declarations that an endpoint has no possible defect:

- A BOLA claim against `/identity/api/v2/vehicle/vehicles` is a false positive because the service resolves the JWT user and queries vehicles by that user's ID ([implementation](https://github.com/OWASP/crAPI/blob/73d309cc8f28bbdeed31dbb35f05dba8354de3c9/services/identity/src/main/java/com/crapi/service/Impl/VehicleServiceImpl.java#L139-L165)).
- A BOLA claim against `/identity/api/v2/user/videos/{id}` is a false positive because the service resolves the token user, fetches that user's video, and requires its ID to match the path parameter ([implementation](https://github.com/OWASP/crAPI/blob/73d309cc8f28bbdeed31dbb35f05dba8354de3c9/services/identity/src/main/java/com/crapi/service/Impl/ProfileServiceImpl.java#L115-L133)). This does not negate the separate excessive-data-exposure finding above.
- Unauthenticated-access claims against `/workshop/api/shop/products` and `/workshop/api/mechanic` are false positives because their `GET` methods carry the project's JWT authentication decorator ([product view](https://github.com/OWASP/crAPI/blob/73d309cc8f28bbdeed31dbb35f05dba8354de3c9/services/workshop/crapi/shop/views.py#L46-L62), [mechanic view](https://github.com/OWASP/crAPI/blob/73d309cc8f28bbdeed31dbb35f05dba8354de3c9/services/workshop/crapi/mechanic/views.py#L125-L142)).

The dashboard is deliberately **not** a safe control. Its service comments that it does not validate the JWT signature and calls `getUserFromTokenWithoutValidation` ([implementation](https://github.com/OWASP/crAPI/blob/73d309cc8f28bbdeed31dbb35f05dba8354de3c9/services/identity/src/main/java/com/crapi/service/Impl/UserServiceImpl.java#L200-L232)).

## Safety exclusions

HTTP `GET` is not sufficient evidence that a crAPI route is read-only:

- `GET /workshop/api/mechanic/receive_report` creates and saves a `ServiceRequest` ([implementation](https://github.com/OWASP/crAPI/blob/73d309cc8f28bbdeed31dbb35f05dba8354de3c9/services/workshop/crapi/mechanic/views.py#L164-L205)).
- `GET /workshop/api/mechanic/mechanic_report` reads another report without an ownership check, but it also calls `service_report_pdf`, which writes a report file ([implementation](https://github.com/OWASP/crAPI/blob/73d309cc8f28bbdeed31dbb35f05dba8354de3c9/services/workshop/crapi/mechanic/views.py#L208-L244)). It is therefore excluded even though OWASP documents it as a BOLA challenge ([solution](https://github.com/OWASP/crAPI/blob/73d309cc8f28bbdeed31dbb35f05dba8354de3c9/docs/challengeSolutions.md#challenge-2---access-mechanic-reports-of-other-users)).

These exclusions are also a runtime safety requirement: a read-only campaign against crAPI must deny the two routes rather than assuming every `GET` is side-effect free. The crAPI target profile therefore denies both exact paths, and `ScopedTarget` enforces that policy before transport or request-budget consumption.

## Scoring semantics

- Coverage is unique matched benchmark cases divided by five expected cases.
- Precision is matched benchmark cases divided by all confirmed claims. Safe-control and
  unscored confirmations both reduce precision; this prevents an open-ended finding from
  escaping the benchmark's false-positive accounting.
- Duplicate findings do not increase either count.
- Confirmed findings outside this deliberately small corpus remain labelled `unscored` rather
  than false positives, but count against precision and fail the showcase acceptance contract
  until a human expands the ground truth.
- Efficiency is total campaign HTTP requests per matched benchmark case; it is `null` when no case is matched.
